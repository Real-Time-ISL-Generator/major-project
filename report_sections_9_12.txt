9.1 Input Handling and User Interaction
The starting point of the application is the user input layer, because every later stage depends on the quality and clarity of what is submitted at this stage. The interface has been designed to support three separate modes of interaction: YouTube URL input, direct text input, and subtitle file upload. This separation is important because each type of input requires a different processing path. A YouTube link leads to subtitle retrieval from the backend, direct text is converted immediately into a playback-ready sequence, and a subtitle file is parsed locally after being selected by the user. By separating these modes rather than combining them in a single uncontrolled form, the system reduces ambiguity and creates a smoother user experience.

Another important design decision in this part of the project is that only one mode is active at any given time. This prevents conflicting input combinations and ensures that the user always knows what the system is going to process. When the submit action is triggered, the panel prepares a clean payload based only on the selected mode. This may seem simple, but it is essential to the stability of the overall application because it avoids accidental mixing of typed text, file content, and video links. The same interface also controls loading state so that repeated clicks do not interrupt the current operation. In addition, the panel includes a clear action that resets the entered values and restores the input area to a neutral state. Theme selection is also preserved so that the interface remains consistent across sessions and improves comfort during repeated use.

9.2 Subtitle Retrieval and Backend API
Once a YouTube link is submitted, the responsibility shifts from the input layer to the backend application. This part of the project is responsible for identifying the requested video, retrieving subtitle data, and returning the required information in a form that the frontend can use immediately. The backend provides a health endpoint for availability checks and a dedicated download endpoint for subtitle acquisition. This separation keeps the external interaction simple from the frontend's point of view while allowing the backend to manage the more detailed processing logic internally.

The retrieval process begins with extraction of the video identifier from the submitted link. Since YouTube links may appear in different formats, the backend includes logic to interpret more than one URL style before deciding which video is being requested. Once the identifier is determined, the backend prepares the configuration needed to obtain English subtitle output in SRT format. The resulting subtitle file is stored under a unique name so that multiple requests can be handled cleanly without collisions. After this stage, the backend returns the information necessary for the frontend to continue with parsing and playback.

This section of the project also includes an important reliability feature. In practical use, subtitle retrieval may not always succeed on the first attempt, especially when additional confirmation is required. To reduce disruption in such cases, the backend contains a retry mechanism that can make a second attempt with cookie-backed authentication data. This improves robustness without forcing the user to change the way they interact with the system. In effect, the backend not only retrieves subtitles but also protects the overall user experience by handling difficult access cases in the background.

9.3 Subtitle Parsing and Semantic Chunk Formation
Raw subtitle text is rarely ready for direct visual playback. It often contains formatting noise, timing irregularities, overlapping windows, and fragments that are too short or too closely spaced to be useful in isolation. For this reason, the project includes a dedicated parsing and chunk-formation stage. This stage acts as the bridge between subtitle acquisition and meaningful playback. Its purpose is not simply to read subtitle lines, but to convert them into a sequence of well-structured units that can support smooth and understandable visual presentation.

The parser first standardizes the incoming content. It handles both SRT and VTT formats, removes headers and note sections, normalizes line endings, extracts timestamps, and cleans unnecessary formatting marks from the text. After this initial pass, the parsed cues are checked for invalid or overlapping timing patterns. If overlapping cues would create duplication in the playback timeline, the system resolves them so that the final sequence remains clean and coherent. This is especially important in subtitle streams where rolling captions or repeated windows may otherwise lead to confusing output.

Once the cues have been normalized, the system moves into semantic chunk formation. Here, the goal is to combine nearby subtitle cues into larger units that feel more natural during playback. Instead of treating every subtitle line as a separate display event, the implementation examines character length, time gap, and overall duration before deciding whether adjacent cues should stay together or be split apart. The current thresholds are specific and deliberate: maxChars = 96, maxDuration = 7.5 seconds, and maxGap = 0.85 seconds. These values help prevent both extremes: overly fragmented playback and excessively long segments that become difficult to follow.

The following excerpt highlights the key decision logic used during chunk formation.

Snippet:
```ts
if (gap > options.maxGap) {
  return true;
}
if (combinedText.length > options.maxChars) {
  return true;
}
if (combinedDuration > options.maxDuration) {
  return true;
}
```
This short rule set is a good example of how the project balances readability and timing. Instead of relying on a single condition, it considers textual density, temporal distance, and duration together before deciding where a meaningful boundary should appear.

9.4 Playback Preparation, Pose Generation, and Viewer Rendering
After chunk formation is complete, the application prepares each chunk for actual playback. At this stage, the text is no longer treated as raw subtitle content but as a structured playback unit with timing, identity, and display-related state. Each prepared chunk includes the text to be presented, its start and end time, an estimated or derived duration, and the information required to request the corresponding visual sequence. This intermediate representation is one of the most important parts of the system because it allows the later stages to operate consistently, regardless of whether the original source was a YouTube link, typed text, or an uploaded subtitle file.

Pose generation is handled through a compact utility that converts the chunk text and language parameters into a request string used by the visual playback layer. Even though the implementation itself is short, its role is central because it connects language content with avatar-ready output. The current implementation uses the language parameters spoken = en and signed = ase. Once this request string is prepared, the viewer layer takes over and becomes responsible for rendering the current chunk on screen.

The rendering layer is designed to do more than simply display animation output. It manages component initialization, responds to lifecycle events, and communicates playback status back to the rest of the application. It also provides visual feedback to the user by showing loading indicators, active playback states, chunk text bubbles, and error overlays. This makes the viewer not just a display surface, but an active part of the overall user experience.

The following snippet shows the compact request-building step that prepares the pose sequence query.

Snippet:
```ts
const params = new URLSearchParams({
  text: trimmedText,
  spoken: spokenLanguage,
  signed: signedLanguage,
});
return `${api}?${params.toString()}`;
```
Although brief, this code is important because it marks the point where processed language content becomes directly usable by the rendering pipeline.

9.5 Playback Synchronization and End-to-End Execution Flow
The final stage of implementation is the orchestration layer, where all previous parts are connected into one continuous process. This logic is handled by the main application component, which acts as the controller for runtime behavior. It receives the submission, resets the previous session state when necessary, coordinates subtitle retrieval or local processing, initializes the playback chunks, and then advances through those chunks in the correct order. The value of this stage lies not in any single function, but in the way it keeps every part of the project synchronized.

When the input comes from a YouTube link, the controller first retrieves subtitle data from the backend and then passes the content through parsing and chunk formation. When the input comes from text or a subtitle file, the controller takes a shorter route but still produces the same internal playback representation. In that sense, different user inputs are unified into one internal execution model. This is a strong design feature because it reduces duplication and allows the same playback logic to operate across all supported modes.

Synchronization becomes especially important during playback. For video-backed execution, the system seeks the source player to the correct segment boundary, starts the corresponding visual output, watches the segment timing, and pauses at the correct moment to avoid overlap with the next chunk. When no source video is involved, a virtual timing mechanism performs the same coordination role. Only after both sides of the playback process are complete does the system move on to the next chunk. This ensures that the visual sequence and timing remain aligned instead of drifting apart over successive segments.

The following short excerpt captures the central synchronization step used during video-backed playback.

Snippet:
```ts
player.seekTo(currentChunk.start, true);
player.playVideo();
monitorVideoSegment(currentChunk.start, currentChunk.end);
return;
```
This part of the controller illustrates how playback is not merely started, but actively guided within defined temporal boundaries. In complete form, the overall execution path of the system can be summarized as follows: User input -> input validation -> subtitle retrieval or local content reading -> subtitle parsing -> normalization -> semantic chunk formation -> playback chunk preparation -> pose request generation -> viewer binding -> synchronized playback -> chunk transition -> completion.

12. CONCLUSION AND FUTURE WORK

12.1 Conclusion
This project has been developed to make spoken or written content easier to follow through a sign-oriented visual presentation workflow. The system accepts three types of input, namely YouTube video links, plain text, and subtitle files, and transforms them into a common internal processing sequence. This sequence includes input validation, subtitle retrieval when required, subtitle parsing, semantic chunk preparation, playback coordination, and synchronized visual rendering. Because these stages are connected through a shared internal structure, the project is able to support more than one type of input without needing entirely separate execution paths for each case.

One of the strongest aspects of the implementation is the way subtitle content is refined before playback begins. Rather than passing raw subtitle text directly into the display layer, the project first restructures the subtitle stream into clean and meaningful playback units. Parsing, normalization, overlap handling, and chunk formation all contribute to this process. As a result, the final playback sequence is more stable, easier to follow, and better suited to timed visual presentation. This is particularly important in real subtitle data, where timing overlaps, formatting inconsistencies, and short fragmented cues can easily reduce clarity if they are not handled carefully.

The project also demonstrates a practical balance between interface design and internal processing logic. The frontend provides multiple ways for the user to interact with the application while still preserving a single coherent execution model. The backend supports the YouTube-based path by retrieving subtitle data and handling retry situations when the first attempt is not sufficient. The playback controller then brings these pieces together and ensures that each chunk is prepared and executed in sequence. From the standpoint of an academic project, this integration is important because it shows that the work is not limited to isolated functions or interface mock-ups; it results in a working system where several engineered components operate together in a meaningful way.

The testing evidence further strengthens the usefulness of the project. Frontend interaction tests, parser tests, and build verification provide direct support for the claim that the implemented features behave as intended. Even where environment limitations prevented backend tests from being executed locally, the presence of dedicated backend unit tests shows that reliability and edge-case handling were considered during development. Taken together, the project can be concluded as a well-structured and functionally meaningful implementation that addresses the problem of subtitle-driven visual interpretation through a coordinated, multi-stage software pipeline.

12.2 Future Work
Although the current version of the project is functionally complete in its main objectives, there are several directions in which it can be improved further. One major area for future work is the refinement of language and sign alignment. At present, the system is already capable of transforming input content into a visual playback sequence, but future development can improve how strongly the language-processing stage aligns with the specific sign-language goals of the project. This would be especially valuable if the work is extended toward broader linguistic coverage, deeper sign-language adaptation, or more specialized educational and assistive use cases.

Another useful direction is performance and scalability improvement. As the application grows, there is value in reducing processing overhead, improving loading efficiency, and refining playback smoothness in longer sessions. The current implementation already supports structured chunk-based playback, which provides a strong foundation for such optimization. Future work could therefore focus on better bundling strategy, finer playback tuning, and more efficient handling of large subtitle inputs. These changes would improve responsiveness without altering the core design of the system.

The project can also be extended with stronger persistence and analysis features. At present, the application focuses on immediate processing and playback. A future version could store user sessions, processed inputs, subtitle histories, or playback-related information for later review. This would be especially useful in an educational setting, a repeated demonstration context, or a research workflow where prior results need to be revisited. In the same way, broader evaluation methods such as usability studies, timing accuracy analysis, and comprehension-focused feedback could add stronger evidence for the practical effectiveness of the system.

Finally, future work may also concentrate on deployment maturity and long-term maintainability. This includes richer integration testing, improved environment preparation, more systematic error reporting, and cleaner support for wider usage conditions. These additions would not change the central idea of the project, but they would help move it from a strong prototype toward a more polished and dependable application. In that sense, the current implementation forms a solid base on which a more comprehensive and mature version of the project can be built.
